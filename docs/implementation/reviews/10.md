## Findings and fixes

1. **P1 — account identity was not unique for nullable owners.** PostgreSQL
   permits multiple NULL-bearing rows under an ordinary UNIQUE constraint, so
   duplicate system, user and organization ledger accounts were possible. The
   ineffective constraint is replaced with three owner-shaped partial unique
   indexes, and get-or-create is serialized by logical identity.

2. **P1 — posted history could acquire new lines.** UPDATE and DELETE were
   blocked, but INSERT remained open after commit; an attacker could append a
   balanced pair without changing an existing row. Entries now freeze their
   expected line count, and a deferred line trigger rejects additions as well
   as incomplete or unbalanced entries.

3. **P1 — idempotency keys did not preserve meaning.** Reusing a journal or
   reservation event with different accounts, currency, amount, reference or
   expiry returned the first object silently. Replays are now compared with the
   persisted accounting effect and conflicts raise `idempotency_conflict`.

4. **P1 — concurrent settlement could overspend a reservation.** Settlement
   and release read an ORM-cached reservation without locking it. Both now
   reload under `FOR UPDATE`; a real two-transaction regression proves that two
   70-unit settlements cannot both consume a 100-unit hold.

5. **P1 — replaying a settlement disposed the hold twice.** The journal replay
   returned the original entry, but the reservation amount was incremented
   again. Settlement now recognizes and validates the existing posting before
   changing reservation state.

6. **P2 — a posting could race an availability calculation.** New journal
   postings lock all participant accounts in deterministic order, sharing the
   same serialization boundary used by reservations. Business-event advisory
   locks also make concurrent retries converge before insert.
