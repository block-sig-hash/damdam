## Findings and fixes

1. **P1 — concurrent planning could race through the idempotency read and
   insert.** Planning now takes a PostgreSQL advisory lock scoped to the
   organization and idempotency key. A concurrent regression proves both
   callers converge on one job.

2. **P1 — an idempotency key could silently identify a different request.** A
   repeat with changed recipients, product, market, currency or unit amount now
   returns `409 idempotency_conflict` instead of returning the earlier job.

3. **P1 — concurrent fund, provision, resume and item mutations were not
   serialized.** Those operations now lock the job row before reading and
   updating its items, reservations, order allocations and counters. A
   concurrent funding regression proves no duplicate hold is created.

4. **P1 — two recipients could redeem the same activation request.** Redemption
   now locks the request row before checking and spending it. A two-session
   concurrency test produces exactly one successful claim and one
   `activation_request_spent` response.

5. **P1 — order totals included invalid and unfunded recipients.** The order
   started at `unit_amount * recipient_count` even when no order item existed.
   It now starts at zero and grows only when a funded item is allocated; the
   partial-funding regression proves two purchased lines total two unit amounts
   even when three recipients were planned.

6. **P1 — runtime local entitlement was disconnected and carrier success could
   be overstated.** The bulk service now shares the application
   `ConnectivityService`, so internet-only products receive the local grant.
   Carrier products remain ordered unless a confirmed outcome is explicitly
   supplied; the test fixture's confirmation switch is not supplier evidence.

7. **P1 — supplier outcome helpers could downgrade an already provisioned
   service to failed or unknown.** Both transitions are now restricted to
   ordered items and otherwise return `409 item_not_awaiting_supplier`.

8. **P2 — an expired activation request was rolled back with its 410 error.**
   The route now commits the expired state before returning the error, and the
   HTTP regression verifies the durable transition.

9. **P2 — the submitted migration and documentation identities collided with
   accepted work.** The integration now follows `0041_organization_people` as
   `0042_bulk_provisioning`; its amendments are data-model §6.58 and API §7.41.

## Remaining gates

- There is no approved carrier adapter, durable supplier dispatch or supplier
  reconciliation path. Runtime carrier items stay ordered. Failures and unknown
  outcomes in the scenario are injected through the same state-transition
  methods a future adapter would call; they do not prove a supplier interaction.
- Funding creates one ledger reservation per serviceable line. It does not
  capture or settle a payment, and the bulk line has no captured payment attempt
  to refund. Provisioned-line cancellation therefore remains refused pending
  the settlement and refund-policy integration.
- Issuing an activation request returns a raw token once, but no email or SMS
  dispatcher sends it. Redemption is implemented; recipient delivery is not.
- The API does not include a dashboard or mobile employee installation handoff.
  An activation request is not evidence of eSIM installation or carrier
  attachment.
- Job counters are service-maintained denormalized values. Normal API mutations
  are serialized on the job row, but direct SQL can still desynchronize them.
