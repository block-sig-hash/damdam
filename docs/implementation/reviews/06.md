## Findings and fixes

1. **P1 — the adopted launch identity had no login or signup flow.** The
   submission could link an email and recover through it only after a phone OTP
   account already existed. Added uniform passwordless email request/confirm
   endpoints, purpose-bound authentication tokens, nullable legacy phone and
   platform fields, and concurrent signup convergence on one verified owner.

2. **P1 — recovery did not revoke already-issued access JWTs.** Deleting refresh
   rows left a compromised access token valid until expiry. Consumer access and
   refresh tokens now carry a durable `auth_version`; email and phone recovery
   lock the user, increment the version, revoke refresh rows and issue the new
   pair in one transaction.

3. **P1 — legacy PIN recovery could create an account and preserve compromised
   sessions.** An unknown recovery number entered the ordinary signup path, and
   a known account received another session without invalidating the old ones.
   Unknown recovery now fails only after successful OTP proof and never creates
   a user. Known recovery invalidates both token classes immediately.

4. **P1 — migration and runtime models could not represent email-only users.**
   Revision 0028 now makes `users.phone_number` and `users.platform` nullable,
   adds the authentication token target fields and `auth_version`, and refuses a
   destructive downgrade while email-only accounts exist. A populated 0027 →
   0028 test proves phone backfill and legacy-only rollback.

5. **P2 — verified OTP accounts did not receive account identifiers.** Every
   successful phone authentication now creates or reuses a verified phone
   identifier. Existing-account updates lock the user before primary-identifier
   decisions.

6. **P2 — primary identity and ownership races were under-constrained.** A
   PostgreSQL partial unique index now allows at most one primary identifier per
   user. Email confirmation promotes the email and demotes the old primary;
   concurrent ownership conflicts map to the stable API error. A proved email
   on exactly one legacy user is adopted by that account, avoiding a duplicate;
   ambiguous legacy duplicates fail closed.

7. **P2 — production-default token delivery retained raw credentials in
   memory.** The recorder is now test-only. Other environments discard tokens
   until a live provider is configured, so a missing provider cannot turn the
   process heap into a magic-link store.

8. **P2 — nullable identity fields broke existing notification paths.** eSIM
   readiness skips WhatsApp when no phone exists, and payment receipts send only
   through channels actually present. Static typing covers both paths.

9. **P2 — the mobile patch changed a handset warning into account state.**
   AC-10.6 requires the eSIM compatibility warning once per device. That change
   was reverted. The local PIN and lockout remain bound to their owning user and
   are cleared on every session-ending path; logout still completes if secure
   storage temporarily refuses deletion.

10. **P2 — the schema change lacked a numbered data-model amendment and
    populated migration proof.** The model, API, security, mobile and testing
    amendments now describe the implemented invariants and tested rollback
    boundary.
