## Findings and fixes

1. **P1 — organization routes bypassed account-recovery revocation.** Their
   private token decoder read only the user id and ignored chunk 06's
   `auth_version`. An access JWT superseded by email or phone recovery therefore
   remained valid on the organization surface. The guard now decodes the full
   identity and compares its version with the current user row.

2. **P1 — a new recovery session inherited an old MFA elevation.** Elevations
   were scoped to user and organization only. They now carry `auth_version`, and
   the authorization query requires it to match the current account generation.

3. **P1 — HTTP MFA failures never reached the lockout counter.** The service
   flushed failed attempts and raised, after which the request context rolled
   the transaction back. Enrollment confirmation, disable and step-up handlers
   now commit the attempt state before re-raising the controlled error. Lockout
   includes a `Retry-After` response header.

4. **P1 — a stolen bearer token could replace active MFA.** Calling enrollment
   again disabled the existing authenticator and every recovery code, then
   returned a new secret without asking for the existing factor. Active MFA now
   refuses replacement. A current TOTP or a single-use recovery code must
   disable it before enrollment can begin again.

5. **P1 — TOTP and recovery codes were not consumed under a row lock.** Two
   simultaneous requests could both validate stale state. Credential and
   recovery-code reads now use `FOR UPDATE` with refreshed identity-map values;
   PostgreSQL concurrency tests prove exactly one request succeeds.

6. **P2 — expired invitations blocked replacement forever.** The partial unique
   index still treated an expired row as pending. Issuance now serializes on the
   organization row, revokes an expired offer and creates its replacement.
   Pending lists exclude expired rows, and revoked timestamps have a database
   constraint.

7. **P2 — listing a user's invitations loaded every tenant's pending offers.**
   Recipient and expiry predicates now run in SQL, so unrelated tenant data is
   neither loaded into the process nor scanned in Python.

8. **P2 — integration collided with accepted specification numbering.** Chunk
   06 owns data-model §6.45 and the calling amendment owns data-model §6.46/API
   §7.33. Organization contracts were preserved and moved to §6.47/API §7.34.
