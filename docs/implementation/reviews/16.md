## Findings and fixes

1. **P1 — usage could be attributed to the wrong carrier line or tenant.** The
   ingesters trusted the supplied `CarrierLine` while ignoring the provider
   reference in the snapshot/event, and a raw `UsageRecord` could pair one
   line with another entitlement. Both ingesters now reject crossed provider
   references, and a composite foreign key binds carrier line and entitlement.

2. **P1 — cumulative counters could double-count or under-count.** An older
   reading arriving after a newer one generated another delta; concurrent
   polls could calculate from the same predecessor; and an explicit new cycle
   whose value exceeded the old cycle was treated as a same-cycle delta.
   Counter ingestion is now serialized per line, retains late raw evidence
   without counting it again, and counts a newly identified cycle in full.

3. **P1 — derived counter resets bypassed the authoritative-source rule.** A
   reset is labelled `DERIVED`, which the original source selection exempted.
   A non-authoritative counter could therefore become billable precisely when
   it reset. Derived counter records now retain counter provenance for source
   selection and stay `EVIDENCE` when events are authoritative.

4. **P1 — concurrent redelivery and cursor work did not converge.** Event and
   cursor get-or-create paths used read-then-insert, and cursor mutations could
   lose updates. Transaction-scoped PostgreSQL advisory locks now serialize
   each event, counter, cursor, correction and exception identity; cursor
   mutation also reloads the locked row. Unique constraints remain the final
   database guard.

5. **P1 — the documented append-only usage history was mutable.** Direct
   update/delete could rewrite evidence, and multiple corrections could point
   to one original. PostgreSQL now rejects mutation except the one-way state
   transition to `SUPERSEDED`, and a partial unique index permits one appended
   correction per original. Correction creation locks and reloads the source.

6. **P1 — charging could leave the ledger inconsistent or debit another
   customer.** A charged correction could omit its revised amount, accounts in
   another currency were accepted, and any same-currency service-credit
   account could be supplied. Charging now requires the revised amount,
   matching currencies, the service-credit/revenue account pair, system-owned
   revenue, and a debit account owned by the order payer.

7. **P2 — provider event ids were treated as globally unique without evidence.**
   The natural key now includes provider line and usage kind before hashing to
   the bounded column, preventing collisions where supplier ids are scoped per
   line or stream.

8. **P2 — the submitted stack predated accepted dependency fixes.** Chunk 16
   was replayed onto the accepted chunk-15 merge, preserving all independently
   reviewed fixes before acceptance.
