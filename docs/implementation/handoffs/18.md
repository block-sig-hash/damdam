## The finding: chunks 09–17 built no HTTP surface

The assignment says "connect" navigation, and the connecting turned out to be
the missing half. Chunks 09–17 delivered models, services and migrations for the
catalog, ledger, orders, payments, refunds, connectivity, usage and spending
controls — and **not one HTTP route for any of them**. `app/main.py` mounts
seventeen routers; every one predates chunk 09.

So a mobile app cannot ask "what do I have" at all. Chunk 18 adds the first
three consumer reads (below). Chunks 19–21 will need the same for catalog and
checkout, lines and usage, and receipts and deletion. Reviewers sizing those
chunks should assume an API half as well as a mobile half.

### The two decisions worth reviewing closely

**1. `delivery` is derived from a carrier line, never from the product.**
`products.kind` has one `voice` value covering both a native-dialer eSIM plan and
an internet-calling plan. The discriminator is instead whether provisioning
actually produced a `carrier_lines` row — an observed fact. An `internet`
service reports `requires_installation: false` and returns
`installation_state: null` / `activation_state: null`, because there is no
profile and no line, and `"not_installed"` would be a false negative rather than
a fact. This is what makes the calling amendment's internet-only journey
possible: without it the app would have to invent an installation step for a
product that has no profile.

**2. `ready_to_use` requires two independent observations, and payment is
neither of them.** A carrier service is ready only when the **device** reported
the profile installed *and* the **carrier** reported the line active, and the
entitlement has not expired. Suspension (chunk 17) is not ready. An expired
entitlement is not ready even though the profile is still installed and the line
still active — and the summary keeps reporting both as true, because telling the
customer otherwise would send them to reinstall something already on the phone.

A third, smaller one: a **failed or cancelled** item does not make the account
`pending`. The customer is not waiting for it. It stays in the list with its own
state so the failure is visible and has a route out (AC-37.5).

### Mobile

- `src/navigation/TabBar.tsx`, `ConsumerApp.tsx` — the four destinations
  (Home / Plans / My Line / Account), hand-built for the reason
  `OnboardingNavigator` gave for its own stack. Every tab is a `tab` role inside
  a `tablist`, carries `selected`, and clears the 48dp target. A waiting
  invitation is announced in the Account tab's accessibility label, not only as
  a silent badge.
- `src/navigation/AuthNavigator.tsx`, `screens/SignIn/`,
  `screens/AccountRecovery/` — email-first sign-in, signup and recovery on
  chunk 06's `/v1/auth/email/**`.
- `src/screens/Invitation/InvitationScreen.tsx` — preview, accept, and a named
  screen for each of expired, already-used, revoked, wrong-recipient and
  already-a-member.
- `src/screens/ConsumerHome/ConsumerHomeScreen.tsx` — no-service, provisioning,
  install-needed, suspended, failed and expired, each with one next action.
- `src/services/deepLinks.ts` — cold **and** warm launch, with the parsed link
  **persisted** before the callback runs.
- `src/api/http.ts` — one request helper for the consumer surface. It
  deliberately does not retry: a GET is safe to retry and a POST is not, and only
  the caller knows which.

### Three mobile changes outside the new files

1. **`PersistedSession.phoneNumber` became optional, and `email` was added.**
   `users.phone_number` is nullable and an email-first account has none. The old
   `readState` rejected any session without one, which would have signed every
   email account out on every cold start with nothing on screen to explain it.
   The new rule is "at least one identifier".
2. **The PIN gate now applies only where a PIN exists on the device**
   (`useSessionGate`'s `hasLocalPin`). The PIN is a local unlock gate (AC-23.5),
   never a network credential, and an email-first account never sets one. The
   old code gated every restored session, which for such an account is a keypad
   no entry can satisfy and a "forgot your PIN" path that needs a phone number
   the account does not have. US-23's own behaviour for phone accounts is
   unchanged.
3. **`InvitationService.find_by_token` was extracted** from `accept_by_token`, so
   the preview does not need a second copy of "hash it, then select on the hash".

## Migrations and compatibility

- **No migration.** This chunk adds no table, column or constraint.
- **Old clients:** the phone/OTP `OnboardingNavigator` is untouched and still
  serves accounts that hold a phone identity. What changed is which door a new
  customer walks through; chunk 06's `adopt_legacy_phone` remains the bridge.
- **Persisted sessions:** a session written by an older build still loads. The
  only relaxation is that a phone number is no longer required *if* an email is
  present; a session with neither is refused, which it previously also was.
- **Rollback:** reverting the branch removes three read-only endpoints and the
  new screens. No irreversible step.
- **Configuration:** none added. No new secret names.
- **Dependencies:** none added, mobile or API. Deliberately — the tab bar is
  hand-built rather than pulling in `@react-navigation/bottom-tabs` and its
  native-screens/gesture-handler/reanimated chain.
