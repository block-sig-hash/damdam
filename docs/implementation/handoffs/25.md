## Result

**Previously** there was no privileged surface for the cases no automatic path
can settle. A supplier attempt whose outcome was lost sat at `outcome_unknown`
until chunk 11's reconciler could reach the supplier; an exception item raised by
chunks 14 or 16 could be read only from the database; a payment that our records
could not account for had no resolution path at all.

**Now** there is one, under `/v1/operations`, and its shape is defined more by
what it refuses than by what it does.

### The four rules the implementation is built around

1. **Reconcile before resolving.** `resolve_supplier_attempt` refuses — it does
   not warn — when the caller has not asserted that somebody asked the supplier
   what happened to the original operation reference. Chunk 11 built that path
   precisely so a lost response is asked about rather than guessed at, and an
   operations screen that lets a human skip it is how a second eSIM gets bought.
2. **Money moves only through balanced entries.** There is no balance column and
   no balance-setting route. A discrepancy is settled by posting a compensating
   entry through chunk 10's ledger, which refuses anything unbalanced.
   Cross-currency compensation is refused rather than converted.
3. **Every action is recorded, and the record is immutable.** The audit row
   carries actor, reason, idempotency key, copied before/after state and — when
   money moved — the journal entry id. `trg_operator_action_immutable` refuses
   `UPDATE` and `DELETE` at the database, the same mechanism chunk 11 used for
   supplier attempt history.
4. **A replay is the same decision.** `uq_operator_actions_idempotency`
   (`kind`, `subject_reference`, `idempotency_key`) plus an advisory lock makes
   a second click return the first decision instead of taking another one.

### Privilege separation is structural, not a permission string

Every route verifies a token minted for the `admin` audience. An enterprise
administrator holds a tenant token for a different audience and receives `401`
— including the owner of the organization whose own lines are being looked at.
There is no operations permission in chunk 07's matrix, so there is nothing to
grant by mistake. Three tests assert this directly.

### Sensitive data

`mask()` shows trailing digits only. Chunk 15's sealed activation material is
not masked — it is **absent from every response shape**, never read and never
joined. A test walks the generated OpenAPI components and fails if any
operations response schema acquires an ICCID, E.164 or LPA field. The request
schema legitimately accepts a whole ICCID: that is what a customer reads out,
and accepting an identifier the caller already has is not disclosure.

**The calling-expansion paragraph is not implemented, and deliberately so.** It
asks this chunk to cover "unmatched provider legs, uncertain hangups, stale
