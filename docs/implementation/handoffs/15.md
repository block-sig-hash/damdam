## The calling amendment applies, and it narrows this chunk rather than widening it

`docs/implementation/VOICE-EXPANSION.md` (9 September 2026) landed on the new
base and adds a requirement to this assignment: *"Keep carrier and internet
adapter capabilities separate… Evidence for WebRTC never closes carrier gates."*
Chunks 15–17 keep carrier lifecycle, usage and control; outbound internet
calling is V01–V05.

Implemented as `AdapterChannel` on `AdapterCapabilities`, enforced in
`__post_init__`: a carrier-channel adapter that advertises `INTERNET_VOICE` is
refused at construction, and an internet-channel adapter that advertises
`NATIVE_VOICE` is refused too. `TelnyxConnectivityAdapter` declares
`AdapterChannel.CARRIER`.

That refusal is the point. Once one adapter can claim both, a browser calling
test starts standing in for proof that a handset can dial from its own dialer on
a visited network, and those are not the same claim. A conformance case asserts
it for every adapter, and the case is exempted from the "explain every withheld
capability" case — the other channel's capabilities are structurally
unavailable, not an evidence gap somebody could close.

Also from the amendment, and **not** implemented here because it is not this
chunk's to assume: a number shared across carrier and internet modes is a target
requiring written supplier and live route evidence. `assign_number` records an
assignment against one carrier line and nothing treats it as reusable elsewhere.

## The contract recheck found three errors in chunk 03's record

`AGENTS.md` requires vendor claims to be checked against current documentation
with the date recorded, so the recheck happened before any adapter code. It read
the OpenAPI **source** (`wireless.json`), which chunk 03 had not — §1 was written
from the rendered reference pages. Three things came out of it:

1. **`GET /sim_cards/{id}/activation_code` exists.** Chunk 03 recorded no
   documented way to obtain the eSIM profile. There is one, returning "Contents
   of the eSIM activation QR code". Without this finding, self-installation would
   have been written up as impossible.
2. **The WDR report path is `/wireless/detail_records_reports`**, not
   `/wireless/detail/records/reports`. The recorded path would have 404'd on the
   first real call — and chunk 16 is built on it.
3. **`esim_installation_status` has a documented enum, `released|disabled`.**
   Neither value means "installed on a device". §1 left room to read it that way.

Also new and material: `SIMCardAction` is fully specified (including
`interrupted`, which is in the response enum and *absent* from `filter[status]`,
so an interrupted action cannot be found by filtering); `data_limit` is settable
per SIM as well as per group; and the WDR **record** schema is not published at
all — only the report envelope. Full detail in API-CONTRACTS.md §4.

**One chunk 03 fixture was wrong and is corrected here.**
`purchase_esims_202_*.json` carried `"actions_in_progress": 0`, an integer, where
the documented type is boolean. The parser follows the documentation; the
fixtures now say `false`. This is exactly what a contract harness is for, and it
is worth Codex confirming I corrected the right side of that disagreement.

## The five things worth reviewing closely

### 1. The purchase is never retried, and the adapter cannot retry it

Telnyx documents no idempotency key on `POST /actions/purchase/esims` — no
header, no body field. So a lost response is `ConnectivityOutcomeUnknown`, which
is deliberately **not** a subclass of `ConnectivityError`: an
`except ConnectivityError` that swallowed it would turn a lost response into a
refusal, and a refusal looks retryable.

`ConnectivitySupplierClient` translates it to chunk 11's `SupplierTimeout`, so
the existing `record_unknown` → `reconcile` → `HELD_FOR_REVIEW` path runs
unchanged. Nothing in this chunk is a second copy of that machinery.

`test_a_lost_response_never_provisions_twice` asserts one supplier call, zero
carrier lines and `OUTCOME_UNKNOWN` on the item. The conformance suite asserts
the same at the adapter boundary, and
`test_an_adapter_that_retries_a_purchase_fails_the_suite` breaks an adapter to
prove the case actually fires.

A **5xx is also unknown**, not a refusal: the request arrived and the supplier
may have acted on it.

### 2. An empty reconciliation lookup is not an answer

This is the sharpest branch in the chunk. Telnyx does not document whether a
just-created eSIM is immediately visible to `filter[tags]`. If it is not, an
empty result is indistinguishable from "the purchase never landed" — the most
dangerous possible answer, because it reads as safe to retry.

`lookup_is_trusted` defaults to **false**, and an empty lookup returns `None`,
which chunk 11 turns into `HELD_FOR_REVIEW`. Turning it true needs a live
account to prove post-purchase consistency, which is API-CONTRACTS.md §2.3
question 2 and D1's to answer.

The lookup also **does not filter by status**, and there is a test for it: the
documented `filter[status]` enum omits every transitional state, so a SIM
mid-registration would be invisible to a status-filtered lookup — arriving at
the double purchase by way of a query parameter.

### 3. Released is not installed, activated is not attached, 202 is not done

Three separate lies a connectivity system tells customers, refused three ways:

- `esim_installations.profile_released_at` is a new column, separate from
  `installed_at`. `record_device_installation` is the only writer of the latter.
  No carrier can observe a handset.
- `record_network_observation` is the only writer of `network_state`. There is no
  branch in `apply_provider_line` that sets it — a carrier saying a line is
  enabled is telling us about its own records.
- `carrier_line_actions` has four states because every Telnyx state change is
  asynchronous. A 202 makes an action `pending`; the line moves on `confirmed`
  and on nothing else. A failed action leaves the line exactly where it was.

`ux_carrier_line_actions_open` allows one open action per line, and
`test_the_open_action_guard_holds_under_concurrency` runs two real sessions
through a barrier to prove the index arbitrates it rather than the service read.

### 4. Activation material is sealed, and the reason is not the usual one

An eSIM activation code is **one-time use**: Telnyx documents that a lost profile
cannot be re-downloaded and needs a fresh purchase. So "rotate it if it leaks"
does not apply — there is nothing to rotate. A leaked code is a paid-for profile
somebody else can install instead of the customer.

- AES-256-GCM with the installation id as additional authenticated data, so a
  ciphertext moved between rows fails to decrypt. Tested.
- `key_reference` names the key and never holds it.
- `fingerprint` is a **keyed** BLAKE2b hash: an unkeyed hash of a structured LPA
  string is reversible by guessing.
- Delivery is a `CredentialGrant` — bound to one person, ten minutes,
  redeemable once under `SELECT … FOR UPDATE`. Only the token's fingerprint is
  stored, so a database dump cannot mint deliveries.
- Every "not redeemable" case returns the **same** error, so a caller cannot
  learn that a token existed.
- `ActivationCredential.__repr__` and `ActivationCode.__repr__` redact, and a
  conformance case asserts a failed fetch names the SIM and never the code.

### 5. `ProductAllowance` is a gap I found in chunk 09, filled here

§6.44 gave `entitlements` exact byte and second columns; §6.46 gave products
prices, coverage and tariffs. **Nothing recorded how much connectivity a product
carries.** Provisioning would have had to invent the number, and a grant invented
at fulfilment time is a grant nobody agreed to.

So `grant_entitlement` reads `ProductAllowance` and refuses with
`product_allowance_missing` when there is none, rather than accepting an amount
from its caller. Chunk 16 needs this to exist before it can reduce anything.

Codex may reasonably judge this belongs in chunk 09's diff instead. I put it
here because this is where the entitlement is first created and where its
absence actually blocks work; nothing is seeded.

## Known gaps and handoff

- **D1 owns everything live.** Missing input: a Telnyx account with test
  credentials, written answers to API-CONTRACTS.md §4.5 questions 1–8, and a
  rate deck. Owner: founder plus Telnyx commercial/technical.
- **Tag-lookup consistency (§4.5 q2) gates `lookup_is_trusted`.** Until it is
  answered, every unknown-outcome purchase stops for a human. That is the
  correct behaviour and it is also operational load somebody will want to
  reduce; reducing it before the question is answered would be the defect.
- **No worker is wired.** `ConnectivityService` is driven by a caller that
  commits between `begin_provisioning` and `dispatch_provisioning`. Wiring it to
  chunk 11's outbox is chunk 20/25 work; the ordering it depends on is documented
  at the method rather than left to a future reader.
- **`disable` versus `standby`.** `set_state(SUSPENDED)` uses standby, because
  the documented difference is IP preservation and standby is the one a line
  comes back from cleanly. `disable` is available separately. If chunk 17 wants
  the cheaper state for long suspensions, that is a policy call.
- **Termination is refused outright.** `DELETE /sim_cards/{id}` is documented as
  irreversible with the profile unrecoverable, so it is not something an adapter
  call does on a worker's say-so. If operations needs it, it needs a person and
  a screen.
- **For Codex:** the moves. `tools/telnyx_probe/contracts.py` and `reconcile.py`
