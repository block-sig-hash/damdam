## Result

The prior promotion validator intentionally failed every signoff after chunk
04 retired obsolete SOS/incoming-call scenarios. It is now a Python
standard-library validator behind the existing shell entry point. It reads the
committed artifact rather than a dirty working tree, binds its filename and
internal SHA to a tested ancestor, refuses any other tracked change after that
commit, checks seven-day UTC freshness including future dates, and requires
exact common plus channel-specific PASS scenarios, physical Android/iOS rows,
channel eligibility/denial evidence, merchant and applicable carrier
configuration, signed artifacts, privacy/payment review, accepted dependency
ancestry, mock-mode disabled and incident/rollback ownership. The template
documents the same matrix. CI runs the validator's negative tests. This is a
structural gate: it cannot prove the truth of external evidence references or
detect untracked remote configuration drift by itself.

After first review, the gate additionally requires a release-owner Ed25519
signature from outside the PR, checks the exact current staging head, rejects
duplicate/indented FAIL tables and runs trusted base-branch code instead of
PR-head code. A matching custom PR-head status is emitted. An administrator
must first install that workflow on `main`, configure its public key, require
`release-signoff/trusted` with strict up-to-date checks and restrict rule/key
administration. The second fresh review found that a PR-head status alone can
go stale after staging advances or the date expires. A required merge queue
now revalidates the merge-group SHA from trusted default-branch workflow code,
and the release owner must freeze staging during that queue window. None of
that bootstrap is done; current protection is
insufficient (`strict=false`, no required PR review). A dishonest authorized
signer could still attest to false evidence; CI cannot prove provider truth.

Android production `release` no longer uses the checked-in debug key; missing
distribution signing, its debug certificate even from a copied keystore, or
screenshot-harness mode fail closed. It requires an externally approved
certificate fingerprint.
The fixture screenshot build has a separate `screenshot` type. iOS Release now
selects production APNs entitlements; no Apple distribution team/profile is
configured. Retired iOS Hajj/location purpose strings were removed, without
inventing microphone permission before a real outbound SDK is integrated.

The mobile English/French screenshot manifest now includes real Home, Account
and Receipts components and Maestro flows on both platforms. Enterprise and
internal browser journey captures remain explicitly pending. The
[release inventory](../release/27-SIGNING-PRIVACY.md) records actual native
permissions, optional SDK data, hosted checkout, signing commands, store and
terms work, accessibility limits and D1–D6 inputs. Numbered amendments update
the affected specs. No schema, API contract or production service changed.

The third fresh review found that iOS Release could still bundle the fixture
app if `SCREENSHOT_HARNESS_MODE=true` was injected. The Xcode Release bundle
phase now rejects that mode; a Linux shell regression tests the exact committed
phase. A signed macOS archive remains unverified and blocked by D6.
The fourth fresh review caught the iOS screenshot CI job still using Release;
it now uses a Debug simulator build with forced JS bundling, and the regression
asserts that the CI install path follows that non-distribution build.
The fifth fresh review found that an ordinary GitHub Actions token could forge
the custom release status, and `.xcode.env.local` could set fixture mode after
the outer iOS Release guard. The trusted jobs now request a status-only token
from a dedicated release GitHub App held in a protected environment; branch
protection must pin that App as the expected source. The iOS guard now runs
after React Native sources both Xcode environment files, with a regression for
the local-env override. The App, environment and branch rules are still D6
administrator work, not installed by this PR.

The first on-demand iOS screenshot run built and installed the Debug simulator
app but Maestro's XCTest driver timed out before any flow; it generated zero
images and is **not** screenshot evidence. CI now waits for simulator boot
completion before installing/launching. A later iOS run passed 34 of 36
