### The design, in the order it happens

1. Record the attempt, **commit**, then call the supplier.
2. Clean response → record it.
3. Timeout or crash → `OUTCOME_UNKNOWN`, then reconcile against the **same**
   supplier with the **same** key. Never a retry of the purchase.
4. Reconciliation cannot say → `HELD_FOR_REVIEW`. A human decides.

Step 1's ordering is what makes step 3 possible: a crash between commit and call
is indistinguishable from a crash after it, and both reconcile identically.

### One finding worth the reviewer's attention

**The idempotency key names a request, not an order item.** The first version
derived it from the order item alone, on the theory that it should be
reconstructible without stored state. Writing the tests found two things wrong
with that: the row is always available (it is committed before the call — that
is the whole point), and a *legitimate* second attempt after a definite
rejection would reuse the key, so the supplier would de-duplicate the new
purchase against the old refusal. The order would never be fulfilled and nothing
would say why. It is now `order-item:<id>:attempt:<n>`.

### Guards that live in the database, not in a code path

- `ux_supplier_attempts_live_item` — one live attempt per order item.
- `uq_supplier_attempts_key` — one attempt per `(provider, key)`.
- `uq_outbox_messages_dedupe` — the same work enqueued twice is one row.
- `uq_inbox_messages_external` — `(source, external_id)`, because providers
  number their own events.
- `ck_outbox_messages_lease` — a lease and its holder move together.

Leases rather than locks: a worker that dies loses its lease and the work
becomes claimable again. Without that a crash strands the message forever and
the order silently never completes, which is worse than failing because nothing
alerts.

## Known gaps and handoff

1. **Chunks 06, 07, 09 and 10 are unaccepted.**
2. **No worker process is wired to this.** `app/worker.py` still schedules the
   legacy Celery tasks. The outbox has no runner: claiming and completing are
   tested directly. Wiring a runner and moving the legacy `esim_issuance_jobs`
   path onto it is a migration in its own right and belongs with the chunk that
   retires the legacy path.
3. **`SupplierClient` has no real implementation.** The protocol is defined and
   tested against a fake that behaves like a supplier on a bad day. A Telnyx
   adapter conforming to it needs D1 and V01's contract, and inventing one from
   documentation would be a mock passing itself.
4. **`reconcile` assumes the supplier can answer by our key.** Chunk 03's
   capability matrix should be checked for whether Telnyx actually supports
   idempotency-key lookup; if it does not, every attempt against it lands in
   `HELD_FOR_REVIEW`, which is safe but is an operational load nobody has
   budgeted. Named here rather than assumed away.
5. **No sweeper for stuck attempts.** `HELD_FOR_REVIEW` rows accumulate and
   nothing surfaces them; chunk 25 owns the exception queue.
