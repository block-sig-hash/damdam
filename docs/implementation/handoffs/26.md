## Result

### 26A — correlation and redaction-safe structured logs

`app/observability.py`. Every response now carries `X-Correlation-Id`; a
client's own id is kept when it is safe, generated otherwise. The id lives in a
`ContextVar` so a service five frames down can log it without it being threaded
through signatures that have no other reason to know about it.

**Redaction is a `logging.Filter` on the root logger, not a helper.** A helper
that callers must remember to call is forgotten exactly once — in the path that
logs a full activation code. As a filter it also covers libraries we did not
write and did not audit, which is where a request body gets logged on debug.

Request logs name the **route template**, not the path: `/v1/calls/{attempt_id}`
rather than a line per attempt id. Raw paths carry customer identifiers into log
search and make every route unique.

The middleware is pure ASGI rather than `BaseHTTPMiddleware`, which wraps the
request in an anonymous task where a `ContextVar` is not reliably visible to the
endpoint — a failure that is silent and only appears under load.

### 26B — production refuses developer defaults

`APP_ENV=production` now fails **at startup** on: the published development JWT
secret; an unset mail provider; an `http://` or localhost browser origin; an
unsigned call-event configuration when live routes are on; and a
`METRICS_SCRAPE_TOKEN` shorter than 32 characters.

Browser origins are now a configured list (`DASHBOARD_BASE_URL` +
`ADDITIONAL_BROWSER_ORIGINS`), which closes the CORS gap V05's handoff flagged
as belonging to this chunk. `security.md`'s V02/V03 amendment assigns browser
origin policy to chunks 25–26; this is 26's half. Secret *rotation* is below.

### 26C — the five numbers somebody is woken up for

`app/metrics.py` plus `GET /v1/admin/metrics` (Prometheus) and
`/v1/admin/metrics.json`. Oldest unprovisioned order, unknown supplier
outcomes, unknown **call** outcomes, webhook lag, quarantined and unmatched
events, usage staleness, and open exceptions by kind.

Carrier and calling failures are separate series, as the calling amendment
requires. Absence is reported as absence — a missing value is omitted from the
Prometheus output rather than exported as `0`.

A scraper gets its own `METRICS_SCRAPE_TOKEN` rather than an operator login,
compared in constant time.

### 26D — rotation, worker durability, least privilege and a measured restore

**Secret rotation now exists, and it closed a hole.** `CredentialVault` refused
any key reference but the current one, so rotating the activation-material key
made every previously sealed profile permanently unreadable. A Telnyx eSIM
profile is one-time-use: "unreadable" means the customer's paid-for line is gone
and the remedy is buying another. The reference recorded on each row told an
operator *which* rows had been destroyed, which is not the same as not
destroying them. The vault now holds retired keys alongside the current one,
seals under the current key and unseals under whichever key a row names.
Rotation is a two-step deployment with no migration.

Keys are selected by reference rather than tried in turn: a vault that attempted
every key would turn "this row names a key nobody configured" into a slow
decryption failure, which is the wrong thing to tell an operator.

**Worker durability was one task deep.** Chunk 15 set `acks_late` on
`app.esim.issue` and got it right; every other task — including V03's deadline
resolver, which enforces call spending bounds — ran on Celery's defaults, where
a task is acknowledged on *receipt* and a killed worker drops it silently. The
settings are now global, because the per-task version is something each new task
author has to remember and the failure of forgetting is invisible.

`visibility_timeout` is deliberately greater than `task_time_limit`, and a test
asserts the inequality: if redelivery could overtake a task that is still
running, a second worker would pick up work in progress — the duplicate-purchase
scenario chunk 11 exists to prevent.

**Least-privilege roles.** `scripts/create-database-roles.sql` separates
`damdam_app` (DML only), `damdam_migrate` (owns the schema, runs Alembic) and
`damdam_readonly` (SELECT, explicitly denied `esim_activation_credentials`).
Separating app from migrate is what makes "no DDL at runtime" structural rather
than a review habit; no role is granted `TRUNCATE`, which would destroy the
ledger while leaving every table in place and every schema check passing.

**The restore drill now measures and reconciles.** It proved point-in-time
recovery before; it did not record how long recovery took, nor whether the
recovered database was *consistent*. It now seeds a balanced double-entry
journal, and after restore asserts the journal sums to zero, that no transaction
is half-present, and that the post-target transaction is excluded whole. A
restore that returns rows is not the same as a restore that returns a consistent
business state, and a double-entry transaction split by recovery is exactly the
failure a row count cannot see.

## Findings from writing it

Two defects were found by the tests rather than by reading, and both are the
kind that fail silently:

1. **The redaction key pattern was anchored on `\b`, which does not fire inside
   `refresh_token`** — `_` is a word character, so there is no boundary between
   `refresh` and `token`. A boundary-anchored pattern silently misses every
   snake_case key, which is most keys in this codebase. Now matched as
   substrings. `idempotency_key` is deliberately exempt: it authorizes nothing
   and it is the field an engineer correlates on when investigating a suspected
   double charge.
2. **`configure_logging` removed every root handler**, which is correct in
   production — where it runs once — and quietly destructive everywhere else.
   Under pytest it removed the capture handler and blinded log assertions in
   every test that ran afterwards; a log shipper's or supervisor's handler would
   have gone the same way. It now replaces only handlers it installed. This was
   caught because two tests passed in isolation and failed in the full suite.
   It also set the root *level* and never restored it — harmless in a process
   that calls it once at startup, wrong to leave behind for a test session.

### One thing not fully explained, and how it was handled

Two middleware tests using `caplog` captured **zero** records in the full suite
while passing in isolation and alongside every subset tried (74 tests across
five files). A logging-state probe after a heavy suite showed nothing anomalous:
no `logging.disable`, no broken propagation, no unexpected level or handler.

They were rewritten to attach their own handler to a uniquely-named logger
rather than to rely on `caplog`. That is the better test regardless: `caplog`
binds to the root logger and depends on global logging state surviving a
thousand other tests, which is a flaky dependency by construction, and the
replacement asserts against the real `LogRecord` the middleware emits — it also
now checks the correlation id is present on a failed request, which the previous
version did not.

**The underlying interaction was not isolated.** Reproducer for anyone who wants
to chase it: run the full API suite with a `caplog`-based assertion on the
`damdam.request` logger. Nothing in application code calls `logging.disable`,
`basicConfig` or `dictConfig`, so the cause is a third-party import.

A third, found by reading: **`NullDeliveryTransport` discards identity email
silently.** Correct in staging, and in production a total authentication outage
that reports itself as healthy — every sign-in link goes nowhere and nothing
logs an error, because nothing failed. 26B refuses to start without a provider.

## Migrations and compatibility

- **No migration.** No schema change, no data touched. `scripts/create-database-roles.sql` is DDL for *roles and grants*, not schema, and has not been run.
- **No dependency added.**
- **New settings**, all defaulted so existing deployments are unaffected:
  `ADDITIONAL_BROWSER_ORIGINS`, `METRICS_SCRAPE_TOKEN`,
  `ACTIVATION_MATERIAL_RETIRED_KEYS`. Documented in `compose.env.example`.
- **Worker behaviour changes on restart.** Late acknowledgement means a task
  interrupted by a deploy is redelivered rather than lost. Every task in this
  worker tolerates that — the provisioning and charging paths write through an
  idempotency key, and the retention sweeps delete-what-expired — but a task
  added later that cannot must revisit the global setting rather than inherit it
  silently.
- **Behaviour change for existing deployments:** an `APP_ENV=production`
  deployment that today runs on the default JWT secret or without a mail
  provider **will stop starting**. That is the intent, and it is a deliberate
  breaking change to catch before a customer does; it needs naming in the
  release notes rather than discovering on deploy.
- **Rollback:** revert; nothing persists.

## Known gaps and handoff

- **Provider outage is not exercised as a scenario.** The acceptance list names
  "provider outage and worker restart"; worker restart is covered by the
  durability settings and their tests, and missing/invalid configuration by
  26B's startup refusals, but there is no test that runs the system with a
  supplier returning errors or timing out. Chunk 11's reconciliation path and
  chunk 12's routing already have their own failure tests from their chunks;
  what is absent is the *integrated* version, which is chunk 28's assignment.
  Named here rather than claimed.
- **`scripts/create-database-roles.sql` has not been applied anywhere.** The
  assignment forbids applying production infrastructure, so it is prepared and
  reviewable but unproven against a real cluster. In particular, the
  `esim_activation_credentials` revoke is conditional on the table existing, so
  the script must be re-run after the first migration that creates it.
- **Migration rollback was not exercised against representative staging data.**
  The restore drill covers database recovery; Alembic downgrade paths across the
  new modules are untested as a sequence, and several chunk migrations document
  their downgrades as development-only. This needs a staging environment with
  representative data, which does not exist yet.
- **The recovery time of 18 seconds is a local figure and not an RTO.** It was
  measured on one developer machine against a small database with MinIO standing
  in for R2. Real recovery time scales with database size and object-store
  latency; the number is evidence the path works and is measured, not a
  commitment.
- **`httpx` logs full request URLs on its own logger**, including path
  identifiers, and that is visible in test output. Redaction does not strip
  them because a customer id in a URL is not secret-shaped. Silencing or
  filtering that logger is a deployment-configuration decision and belongs with
  26D's logging configuration rather than being hard-coded here.
- **The metrics endpoint is uncached and queries live.** Correct at this scale —
  indexed counts and two `MIN`s on an admin-only path — and worth revisiting if
  the exception table grows large.
- **No production infrastructure was applied and no spend was incurred**, as the
  assignment requires. Everything here is configuration and code.
- **No merge, deployment, store submission, vendor message or live purchase.**

Claude's handoff is a request for review, not acceptance.
