## What changed, by tier

### Server

Retired endpoints answer **410** with a stable body —
`{"error": "feature_retired", "details": {"feature": …, "upgrade_required":
true}}` — declared in the OpenAPI contract, not merely returned. `410` rather
than `404`, because the feature is gone deliberately and a client must not read
the refusal as a routing fault worth retrying; `410` rather than a success
envelope, because the original defect was a client being told an SOS alert had
been raised when no operator would ever see it.

Retired: check-in create/history and the Meta WhatsApp delivery webhook; every
SOS path on both traveler and operator sides; the admin SOS retry queue; family
and emergency contacts; the arrival-geofence lookup; `POST /voice/token`; and
the six CLI verification endpoints.

Four Celery beat entries are gone, four of which polled every 10–30 seconds.
Their **task names stay registered as refusals** that dispatch nothing and open
no database session, because deleting the names would leave a beat process on
the previous schedule, or a message queued before the deploy, crashing its
worker in a retry loop.

`GET /voice/eligibility` no longer returns `cli_not_verified` — that gate was a
launch dependency on a deferred feature nobody can enrol into, so every user
would have been reported permanently ineligible to call.

### Two boundaries I moved, and why

1. **Arrival geofencing spans both tiers.** 04C removes the mobile client, so it
   also retires `GET /packages/{id}/geofence`. Removing only the caller would
   have left a live endpoint for a retired feature.
2. **The operator welfare roster is a server projection, not a screen.**
   `GET /hto/pilgrims` reported `last_checkin_at` and `sos_status` for every
   person on a manifest, and the dashboard ranked people by them. Deleting the
   SOS pages alone would have met the letter of the assignment while leaving
   exactly the welfare tracking `SCOPE-DISPOSITION.md` says must not be quietly
   retained. The fields, the queries behind them and the risk sort are gone. An
   operator can still see who is on a manifest and their activation state; they
   can no longer see where anyone last was or whether they are in distress.
   **This is a breaking response change**, and its only client is updated in the
   same commit.

## Result

### The defect, confirmed in code before anything changed

`docs/implementation/retirement/INVENTORY.md` §4 records the full inspection.
In summary, at base `12582f1`:

- `checkin_outbox` and `sos_outbox` were created with
  `client_generated_id, timestamp, latitude, longitude` — **no owner column** —
  in one device-wide file, `damdam-safety.sqlite`.
- `pending()` in both was `SELECT ... ORDER BY timestamp ASC` with **no owner
  predicate**, returning every queued row on the device.
- `performSync()` iterated those rows and called `send(item)`, bound to whatever
  access token was current when the service was constructed.
- `AuthenticatedApp.tsx` memoised both services on **`accessToken` only**. No
  user identity took part in construction, filtering or dispatch.
- `clearSession()` reset the Keychain and nothing else — it did not clear the
  queues and did not stop the 10-second sync timer.
- `PersistedSession` had no user id, so the client could not even name an owner.

**The failure:** A queues offline and signs out; B signs in; the timer fires;
A's rows are POSTed with B's token. The server derives the owner from that
token, so the record is genuinely created as B's. **No server-side check can
detect this** — the mechanism being subverted is the one the server trusts.

### What 04A changes

**Ownership is a required constructor argument, not an optional one.** A default
would leave a forgetful caller with a silently dead queue; a compile error is the
better failure. TypeScript located all 13 call sites.

**Legacy rows are quarantined, never adopted.** Rows with no owner move to
`<table>_quarantine` with a timestamp and reason. They are **kept** — they are a
user's data — and never attributed to whoever signs in next. Quarantine runs on
every initialize, so an interrupted migration converges.

**Ownership is a function, re-resolved at dispatch time**, not a value captured
at construction. That is what makes the delayed-callback case safe: a response
arriving after the account switched neither confirms nor consumes the row.

### Deliberate consequence, stated plainly

A session persisted before this change has no `userId`, so it **owns nothing**:
its queues are inert and it cannot enqueue. That is the correct direction to fail
— an event that cannot be attributed to an account must not be sent, and these
features are being retired anyway — but it is a real behavior change for an
existing install, not an oversight. Flagged for review below.

1. **`ownershipHolds` is checked three times per item** — before the loop, before
   the send, after the send. That is deliberate, and the delayed-callback test
   fails if the third check is removed. It does mean an account switch mid-batch
   leaves the remainder queued rather than erroring; I judged silent preservation
   better than a thrown error in a background timer, but it is a judgement call.
2. **Quarantine is keyed on `client_generated_id` with `INSERT OR IGNORE`.** If a
   later build ever reissued the same client id for a different row, the second
   would be dropped from quarantine. Given these ids are UUIDv4 from
   `react-native-uuid`, I treated that as acceptable.
3. **`useConnection` is a test seam on a production class.** The alternative was
   injecting a connection factory through three call sites for a module being
   deleted in 04C. If you would rather have the factory, it is a small change.
4. **`sql.js` is a new dev dependency.** It is the only way I found to test real
   SQLite on CI's Node 20 without a native build. If you object, the fallback is
   asserting emitted SQL, which is materially weaker and would not have caught
   the missing `WHERE` clause.
5. **`userId` is optional on the session types.** It has to be, for sessions
   persisted before this change. That optionality is what produces the inert-queue
   behaviour; making it required would strand existing users at a type error
   rather than a safe no-op.
6. **The server still trusts the token alone.** A defence-in-depth option is to
   send the client's claimed owner and reject a mismatch server-side. That needs
   an `api-spec.md` contract change, so I left it for 04B where the API is
   already being amended. Worth your view on whether it belongs there.
