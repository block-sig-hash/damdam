## Result

One additive migration, `0027_core_domain_model`, three new model modules and a
shared money type. **Nine tables created, nothing altered, nothing dropped, no
row written, no backfill.**

### The identities

`legal_entities` (seller), `products`, `product_prices`, `orders`,
`order_items`, `entitlements`, `esim_installations`, `carrier_lines`,
`assigned_numbers`. `users` and `organizations` are reused for payer and
recipient rather than duplicated.

**Payer and recipient are roles on a purchase, not new party tables.** A
`parties` table would duplicate identity that `users` and `organizations`
already own. An organization paying for a person's line is the case that breaks
any model where seller, payer and recipient collapse into one user id, and it is
the case the enterprise chunks are built around.

**`legal_entities` is deliberately empty.** Which entity sells is decision D3,
which is open. Seeding a placeholder would put a false answer in the one column
whose purpose is to record the true one.

### The separated states

| Resource | Column | Question |
|---|---|---|
| `orders` | `payment_state` | did anyone pay |
| `order_items` | `provisioning_state` | did the supplier fulfil it |
| `esim_installations` | `installation_state` | is the profile on a device |
| `carrier_lines` | `activation_state` | is the line live with the carrier |
| `carrier_lines` | `network_state` | is it attached right now |

The legacy `packages.status` mixes payment, lifecycle and commercial outcome in
one ordered column, and `esim_profiles.status` (`issued → downloaded →
activated`) mixes supplier, handset and network. They can disagree in reality,
so a single status has to lie about at least one of them.

`provisioning_state` carries **`outcome_unknown`** as a first-class value, not
an error, so a supplier request whose response was lost has somewhere truthful
to sit and is reconciled against `order_items.operation_reference` rather than
retried as a fresh purchase. `network_state` defaults to `unknown` and is never
inferred from activation — reporting "attached" because we activated a line is
how a support agent ends up telling someone their phone works when it does not.

### Money and units

`NUMERIC(20,6)` with a required ISO 4217 `currency` beside every amount, and
`NUMERIC(20,10)` for rates because rates multiply and their error compounds.
There is no default currency and no bare amount. Presentation scale is per
currency and belongs at the edge; cross-currency addition is chunk 10's rule to
enforce, and nothing here pretends a column type can do it.

Entitlements count **bytes and seconds**. The legacy `NUMERIC(6,2)` gigabyte
balance cannot represent a supplier's byte-level usage report without rounding,
and rounding a balance against the customer is a billing defect.

### A defect I introduced and fixed

The currency and E.164 checks use PostgreSQL's `~` operator. Adding them put the
new tables into `SQLModel.metadata`, so the SQLite `create_all` that the fast
unit suite uses began failing to parse the DDL — **225 errors across the whole
API suite**, not just the new tests. Fixed with `ddl_if(dialect="postgresql")`,
matching the `postgresql_where` partial-index precedent already in the codebase.
The constraints are therefore enforced only where the application actually runs,
and everything depending on them is tested against PostgreSQL.

## Migrations

- **Revision:** `0027_core_domain_model`, down-revision `0026_i18n_locales`.
- **Additive only.** No `ALTER`, no `DROP`, no `UPDATE`. New tables start empty.
- **Backfill: none, deliberately.** The full reasoning is in
  [CORE-MODEL-UPGRADE.md](../CORE-MODEL-UPGRADE.md). In short, a backfill is a
  translation and a translation is only correct with respect to how the result
  is read — and nothing reads these tables yet. It would also have to invent a
  selling entity (D3 open), a product mapping (chunk 09's) and a state split for
  exactly the rows where payment and provisioning genuinely differed.
- **Phases:** documented as add-nullable (this chunk) → backfill (chunks 09–11,
  with their consumers) → constrain (a later revision, after a count proves no
  nulls remain) → retire legacy schema (not scheduled).
- **Irreversible steps: none in this chunk.** That is the property that makes
  0027 safe to deploy ahead of the work that uses it, and it is proved rather
  than asserted — the downgrade test compares a full snapshot of a populated
  database either side of upgrade-then-downgrade.
- **Secrets:** none added or referenced.

## Open gates and known limitations

1. **D3 (selling legal entity) is OPEN**, so `legal_entities` has no rows and
   no order can be created until one is decided. That is intended: the table
   makes the gap visible instead of implying an answer.
2. **Nothing uses these tables yet.** They are anchors for chunks 09–11 and 15.
   Coverage of the new modules comes from constraint tests, not from application
   paths, because there are no application paths.
3. **No API contract change.** The assignment allows for one "where applicable";
   no endpoint reads or writes the new tables yet, so adding one would be
   inventing a contract ahead of its behavior.
4. **`product_prices` versioning is minimal.** Effective windows and a version
   integer, no overlap constraint. Chunk 09 owns quote immutability and
   expiry, and an overlap rule written now would likely be the wrong one.
5. **Chunk 04 interaction.** Both branches start from `12582f1` and neither
   touches the other's tables, but they will need a merge order once both are
   accepted. Chunk 04 changes no schema at all, so either order works.

## Refactoring concerns and tradeoffs for Codex

1. **`NUMERIC(20,6)` rather than integer minor units.** Minor units are the
   more common choice and remove scale questions entirely. I chose decimal for
   continuity with the existing `NUMERIC` NGN columns and because metered usage
   rates need sub-minor-unit precision that an integer minor-unit column cannot
   express without a second scale convention. If you prefer minor units, now —
   before anything writes a row — is the cheapest possible moment to change it.
2. **The currency CHECK is a shape check, not an allow-list.** Enumerating
   valid currencies in the database means migrating every time the product sells
   somewhere new, and failing closed on a currency the catalog already accepted.
   Which currencies may be sold in is catalog policy (chunk 09).
3. **`entitlements.order_item_id` is unique**, so one item grants one
   entitlement. A quantity-5 item that should grant five separate entitlements
   would need that relaxed. I judged one-grant-per-item the honest default and
   would rather chunk 23 relax it deliberately than have it be accidentally
   possible now.
4. **`esim_installations` is a new table rather than a column on
   `esim_profiles`.** It keeps the legacy table untouched and its history
   intact, at the cost of a join. The alternative mutates a table chunk 04 is
   concurrently retiring behavior around.
5. **`ddl_if(dialect="postgresql")` means the fast unit suite runs without those
   constraints.** That is a real gap: a unit test can create a row the
   production database would refuse. The mitigation is that everything relying
   on them is tested against PostgreSQL, but if you would rather the SQLite path
   disappear entirely, that is a bigger change than this chunk.
