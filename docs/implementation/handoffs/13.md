## The block, first

The chunk is titled *"Implement the selected global payment adapter"*. **There
is no selected global payment adapter.** `DECISIONS.md` D4 is OPEN and records
Stripe as a candidate, not a decision.

The assignment anticipates exactly this and says what to do: *"Use the global
processor actually selected in the decision register. Stripe is a candidate, not
a settled choice. Without a selection, finish conformance tests and the adapter
boundary, then mark provider-specific work blocked."*

So that is what was built, and the block is enforced rather than noted:

- `test_no_global_processor_adapter_exists_yet` asserts Paystack is still the
  only qualified adapter. Adding a second without qualifying it fails here.
- `test_the_repository_contains_no_stripe_integration` parses every `app/**`
  module with `ast` and fails on a Stripe import, name, attribute or string
  literal. Prose explaining that Stripe is a *candidate* is allowed; code is
  not.
- `CURRENT_CONFIGURATION.processor is None`, asserted. A default naming a
  candidate would sit in code reading like a decision that was made.

**What is needed to unblock, and who owns it:** a recorded D4 decision naming
the processor and evidencing merchant approval — founder/product, per
`DECISIONS.md`. Nothing in engineering's control moves it.

### The conformance suite

Ten cases, each stating the incident it prevents, expressed against
`PaymentProcessorAdapter` and nothing else. Running it against a new adapter is
how a processor is qualified; running it against Paystack today is how we know
the contract is satisfiable by a real integration rather than only by a fake
built to fit it.

The cases cover what the assignment names — asynchronous success, abandonment,
decline and ambiguous outcomes — plus the ones that cost money: a one-way
minor-unit conversion, an unrecognised status treated as success, a transport
failure treated as a decline, a re-serialised webhook body, reordered delivery.

**`test_a_broken_adapter_fails_the_suite`** exists because a conformance suite
that passes for any input is worse than none: it creates confidence in a
qualification that never happened.

### Wallets

Availability is a conjunction of four conditions — a selected processor
supporting the wallet, a live merchant, a registered domain, and a device that
offers it — and **all four are false today**. `is_available` returns the reason,
ordered so the most useful one comes first: "no processor is selected" helps
whoever is debugging more than "your device does not offer Apple Pay", and both
are true.

Card fallback is required whenever a wallet is unavailable, which is always: a
checkout offering only a wallet, on a device without one, is a checkout nobody
can complete.

**No store billing.** Asserted by test across `app/**` for `storekit`,
`in_app_purchase` and `billingclient`. The assignment forbids it, and the reason
is worth restating: store billing takes a commission on the sale and applies
store rules to a service the stores do not provide.
