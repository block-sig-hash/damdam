### What each invariant is enforced by

| Property | Enforced by |
|---|---|
| Every entry balances, per currency | A **deferred** constraint trigger, checked at COMMIT |
| Posted history is never edited | Immutability triggers on UPDATE *and* DELETE |
| One business event posts once | `uq_journal_entries_event` |
| No cross-currency arithmetic | Two composite foreign keys on `journal_lines` |
| A reservation cannot overspend | `SELECT … FOR UPDATE`, proved under concurrency |

The deferred trigger is the design decision worth reviewing. An entry's lines
are inserted one at a time, so a per-statement balance check would fail on the
first line of every legitimate entry. Deferring to COMMIT also means a
half-written entry cannot survive a crash.

### Three decisions later chunks must reuse

1. **`business_event_id` is caller-supplied and meaningful** —
   `order:<id>:capture`, not a random UUID per attempt. A random id makes every
   retry a new event and defeats the constraint entirely. The idempotency lives
   in the naming.
2. **Releasing a reservation posts nothing.** Nothing moved, so there is nothing
   to reverse; a journal entry for a released hold would invent a transaction
   that did not happen. Settlement is the only reservation operation that posts.
3. **Corrections are new opposite entries**, never edits. The trigger refuses
   both UPDATE and DELETE, so this is not a convention anybody can forget.

### The backfill's refusals

`app/ledger/backfill.py` is a re-runnable operation with a reconciliation
report, deliberately **not** a migration step — a backfill inside a migration
runs once, unwatched, with no report anyone reads. What it declines to do is the
substance:

- **No `SERVICE_CREDIT`.** The legacy product had no wallet; every payment
  bought one package outright. Creating a balance would put a liability on the
  books that no event produced.
- **No gigabytes converted to cash.** That would apply a pricing decision
  nobody made, retroactively, to customers who never agreed to it.
- **Posts at `transactions.created_at`**, the only date the legacy table has.
  Writing this found that there is **no payment timestamp** on `transactions` —
  `receipt_sent_at` is a different event, sometimes days later — so inferring
  one would have been exactly the unsupported assumption the assignment warns
  against. Recorded rather than guessed.

## Known gaps and handoff

1. **Chunks 06, 07 and 09 are unaccepted.**
2. **The backfill has not been run against production-shaped data.** It is
   tested against fixtures; the real `transactions` table is not available here.
   Run it `dry_run=True` first and read the report — that is what it is for.
3. **No reservation expiry sweeper.** `expires_at` is recorded and nothing acts
   on it. Deliberate: implicitly releasing money a supplier is about to charge
   for is worse than holding it, so the sweep needs a policy decision (D5) about
   what an abandoned hold means.
4. **No `RESERVED` or `CONSUMED` account is posted to yet.** They exist in the
   enum because chunk 11's fulfilment and V03's usage settlement need them; this
   chunk holds against `SERVICE_CREDIT` directly and settles to `REVENUE`.
5. **`trial_balance` is not scheduled.** Chunk 14 owns scheduled reconciliation;
   the primitive is here.
