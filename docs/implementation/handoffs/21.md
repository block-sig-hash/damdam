## Result

### Previously

The account area did not exist. `DELETE /v1/me/account` soft-deleted with no way
to find out beforehand whether it could; there was no device list, no receipt a
customer could read, no way to ask a question with the order attached, and no
record of what anybody had chosen to be told about. `refresh_tokens` knew whether
a session was valid and nothing a person could recognise it by.

### Now

A customer can see which devices are signed in and sign one out, read a receipt
for anything they bought, ask a question with the order or line already attached,
decide what they are told about, ask for a copy of their own data, and — before
pressing anything irreversible — find out **why** their account cannot be deleted
yet.

**API — new `app/account` package (10 endpoints under `/v1/me`):** sessions
(list, revoke one, revoke all), receipts (list, one), support requests (open,
list), notification preferences (read, set), the deletion preflight, and the
export request.

**Mobile — new `src/screens/Account/`** (`AccountFlow` plus five screens),
`src/api/accountClient.ts` and `src/services/accountCache.ts`. The Account tab
stops being a placeholder.

**Schema — migration `0038_account_and_support`, four new tables:**
`account_sessions`, `support_requests`, `notification_preferences`,
`account_export_jobs`. Additive; `refresh_tokens` is untouched. Documented as
[data-model §6.54](../../data-model.md) and
[api-spec §7.38](../../api-spec.md).

**The decisions a reviewer should look at:**

1. **Not-yours and never-existed are the same answer.** Every ownership failure
   is 404 with the same body. A 403 confirms the id is real, and a confirmed id
   is all somebody needs to enumerate another customer's sessions or orders one
   guess at a time.
2. **The deletion preflight returns reasons, not a boolean.** A customer told
   "you cannot delete your account" closes the app; a customer told "your
   organization still has other members" knows what to do. The internal `detail`
   is **not** returned — it can name another member's line.
3. **Deletion blockers are a registry, not a hard-coded list.** `LIABILITY_PROBES`
   in `app/account/deletion.py` is the seam. This branch's base has no calling
   tables — V02 and V03 are unmerged — and the calling amendment requires active
   call liabilities and grant revocation to block deletion. A registry lets V03
   add its probe where it lives instead of this module importing a table that
   does not exist, or a later chunk quietly forgetting. **This is the single most
   important thing for the reviewer to check gets connected.**
4. **Revoking a session revokes the token, not the row.** `account_sessions`
   describes; `refresh_tokens` is what authentication checks. The token is
   written first, so the worst outcome of a failure between the two writes is a
   session that still shows in the list after it stopped working — never one
   that vanished from the list and kept working.
5. **An absent preference is not a decision.** `GET` returns only what has been
   decided, so a new account gets an empty list rather than defaults dressed up
   as choices; an explicit `false` outlives a later change to the default.
6. **A receipt is rendered from history.** Amounts come from the recorded order
   and its items, never re-priced from the catalog, and cross as strings.
7. **Support references are random, not sequential.** A sequential ticket number
   leaks how many customers have a problem and lets anyone holding one guess
   another; the alphabet omits characters people mistype reading aloud.
8. **Retired features are not re-introduced as preferences.** The categories are
   `low_balance`, `expiry` and `order_status`. A safety or location category
   would be that feature, switched off.
9. **Only receipts are cached on the device, and the cache is keyed by account.**
   A receipt cannot change after the fact, so it is safe on disk and useful
   there. A device list, a preference set and a deletion preflight are decisions
   *about now*: a cached device list shows a revoked phone as signed in, and a
   cached preflight offers a delete button the server has since decided to
   refuse. Those load or say they could not.
10. **Signing out clears this account's slice by prefix.** The handset is shared
   in this market, and every isolation guarantee the API makes is undone by one
   receipt list left on disk for the next person who signs in. Clearing by
   prefix rather than from an index means a slice added later is cleared without
   anybody remembering to come back for it.
11. **Cached content says it is cached, and says when.** Rendering it silently
   is how a customer concludes a refund never arrived from a screen that never
   looked.

## Migrations and compatibility

- **Numbering collision, deliberate.** `0038` is also taken by
  `0038_call_authorization` on the unmerged V02 branch, and this chunk's
  data-model section number (§6.54) collides with V02's. Both branches were cut
  from the same `0037` head to run in parallel at the founder's direction.
  Whichever merges second renumbers; guessing a free number now would be wrong in
  a way that is harder to notice than a conflict.
- **Fresh install:** four tables, six enum types. Every endpoint answers; a new
  account sees empty lists, which is the honest answer rather than defaults.
- **Old-data upgrade:** additive only. `refresh_tokens` is not altered, so
  sessions that existed before this migration simply have no description — they
  appear once their next sign-in records one. No backfill is attempted, because
  inventing a device label for an existing token would put a guess in front of
  somebody deciding what to revoke.
- **Old-client compatibility:** every endpoint is new. `DELETE /v1/me/account`
  is unchanged in contract and behaviour. `app/i18n/catalog.py` gains four keys
  per locale and changes none.
- **Rollback:** `alembic downgrade 0037_spending_controls`. **Development only:**
  it discards support correspondence, and `AGENTS.md` is explicit that history is
  not erased because a surface was removed.
- **Configuration:** none added. No new secret names.
- **Dependencies:** none added.

## Known gaps and handoff

- **Offline installation guidance and timestamped usage are not cached yet.**
  The cache has slices for both (`installation`, `usage`) and nothing writes
  them: My Line owns that data and belongs to chunk 20, so writing it from the
  account flow would put one screen's data behind another screen's loader. The
  mechanism is here; the two call sites are not.
- **Profile editing is read-only.** The screen shows the name, phone and email
  and offers no way to change them. Identity changes run through chunk 06's
  verification flows — an email change is a verification, not a field edit — and
  wiring a text input to those belongs with whoever owns that path.
- **"Sign out everywhere" cannot spare this device from the app.** The API takes
  `keep_session_id`, and the app does not know its own session id, so the flow
  always signs out everything and returns the customer to sign-in. The confirm
  screen offers both options; the "others only" path currently behaves like the
  full one. **The one place the UI promises more than it delivers**, and it
  needs the session id threaded through authentication to fix properly.
- **The liability probe seam is empty in this branch.** Nothing registers a
  probe, so today deletion never blocks on a call. V03 owns
  `call_attempts`/`call_charges` and must register one that blocks on an
  unsettled charge, a held reservation and a live grant. Until then the calling
  amendment's *"include active call liabilities and grant revocation in
  deletion/export; do not delete pending settlement records"* is **only half
  satisfied** — the mechanism exists, the probe does not.
- **The export has no delivery.** A job row is created; no worker builds a file,
  no storage is chosen and no download endpoint exists. `build_export` produces
  the payload and is tested, so what is missing is delivery and its retention,
  not the content.
- **A receipt's product name is a live lookup.** Renaming a product renames it on
  old receipts. Recording the name at purchase belongs to whichever chunk owns
  invoicing; a read model should not change the schema for it. Flagged rather
  than fixed.
- **"Sign out everywhere" names the device to spare, rather than inferring it.**
  An access token does not carry the id of the session it came from, so the
  endpoint takes `keep_session_id` and verifies it against the caller's own
  device list; omitting it signs out everything including this device, which is
  the right default for a stolen phone. Threading a session id through
  authentication would be the more elegant answer and is an auth-path change
  this chunk should not make quietly — noted for whichever chunk owns that path.
- **For Codex:** the registry in `deletion.py` is global mutable state, which is
  the kind of thing a reviewer should dislike on sight. The alternative — this
  module importing every chunk that might block a deletion — is worse, but the
  argument is worth having.
- **No merge, deployment, store submission or production deletion was
  performed**, and none is authorized by this assignment.
