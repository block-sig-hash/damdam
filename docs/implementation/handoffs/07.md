## Result

### Previously

An organization had **one** email and **one** password hash on `organizations`.
Everyone who administered the account shared them. That single fact produces
every US-29 failure at once: no action has an actor, one person's access cannot
be removed without changing everyone's, no second factor can be required of
anybody in particular, and a person cannot belong to two organizations except by
holding two passwords.

### Now

Delivered as four subchunks on one branch, one commit each.

**07A — memberships and the permission matrix** (`ffa2683`)

`organization_members`: one row per `(organization, person)` pair, for the life
of the pair. Revocation is a status change, never a delete — a deleted row
cannot explain why an order placed last month was authorized, and re-adding
someone would race the row that was supposed to be gone. The unique constraint
is also what makes an invitation replay safe.

The matrix (`permissions.py`) is **data**, read on every request. A role added
later with no matrix entry fails at import, rather than quietly authorizing
nothing or being handled by some caller's `.get(role, ALL)`. Owner /
administrator / billing / member, with billing deliberately holding money and no
people: whoever pays the invoices has no business changing who can sign in.

Escalation is refused in both directions — nobody grants a role above their own,
nobody edits their own membership — and the **last owner** cannot be demoted or
revoked. The owner count is read under `SELECT … FOR UPDATE ORDER BY id`.
`ORDER BY id` is load-bearing: two transactions locking the same set in
different orders deadlock instead of queueing.

**07B — recipient-bound invitations** (`ffa2683`)

The binding is the **verified identifier**, not the link. Acceptance requires
the accepting account to hold a verified `account_identifiers` row equal to the
invited address, so a forwarded link, a leaked mailbox archive or a guessed id
is worth nothing — and an *unverified* claim on the address is worth nothing
either. Acceptance claims the row with `UPDATE … WHERE status = 'pending'`, so
two simultaneous clicks produce exactly one membership. An inviter must hold
`MEMBER_INVITE` **and** be allowed to grant that role, so "invite" cannot be a
one-step route to owner.

**07C — administrator MFA** (`b5ed905`)

TOTP on the standard library. No new dependency — the algorithm is twenty lines
of HMAC, and a package here would need an `aarch64` check
(`scaling-infrastructure.md` §12.2) for no benefit.

Correctness is asserted against the **published RFC 6238 Appendix B vectors**,
SHA-1, SHA-256 and SHA-512, not by round-tripping our own generator against our
own verifier — which would pass for a wrong implementation too. The
authenticator on the customer's phone is the external party that has to agree.

A code is **spent** when used (`last_used_counter`), so one seen over a shoulder
is not good for the rest of its thirty-second window. Wrong codes carry the PIN
service's attempt limit and lockout; a *replay* is reported separately and costs
no attempt, so a double-click is not a thirty-minute outage.

Step-up is a row scoped to `(person, organization)`. That is what makes
AC-29.5's "immediately" true rather than aspirational: revoking a membership,
changing a role or disabling the credential drops every live proof **in the same
transaction**. Proving a second factor for one tenant is never proof for
another. Reads never require step-up — second factors that gate reads get
shared, written down or turned off.

**07D — isolation across the surface** (`eef5bf2`, `e47fe25`)

One guard, `require(...)` / `require_tenant(...)`, on every organization-scoped
route including the legacy `/v1/hto/**` ones. A handler that re-checked a role
locally would be a second copy of the matrix, and the second copy is the one
that drifts — which is exactly the failure AC-29.4 describes.

`app/organizations/ownership.py` keeps personal lines separate from
organization-paid ones and refuses cross-tenant reassignment by request
parameter.

### Two defects found and fixed while writing the API tests

1. **An expired session was reported as a cross-tenant refusal.** `resolve_tenant`
   returned `not_a_member` (403) for a token that was merely expired, leaving a
   client unable to tell "sign in again" from "not your organization".
   Authentication and authorization are now separate answers: 401
   `invalid_access_token` for a missing, malformed or expired credential; 403
   `not_a_member` only for a caller who **is** authenticated. Neither answer
   says anything about the target — a nonexistent organization and someone
   else's return byte-identical responses, asserted by test.
2. **The legacy shared credential could still reach privileged routes.** It is
   now refused for every `STEP_UP_PERMISSIONS` entry with
   `shared_credential_forbidden`. This is what makes "replace shared
   organization credentials" real *before* the dashboard has migrated: the
   shared password can no longer add people, change roles or touch billing
   settings, while the manifest and reporting flows it does open keep working.

### The controlled migration, and what it deliberately does not do

`0029_organization_memberships` gives each existing organization **one pending
owner invitation** addressed to the contact already on its row. The exclusions
are the substance:

- **No user account is created.** Manufacturing an account for an address nobody
  has proved is the auto-promotion the assignment forbids, and it cannot be
  undone by whoever later turns out not to own that mailbox.
- **Nobody becomes an owner.** The organization gains its first owner when a
  person proves they can read the mailbox and claims the offer.
- **No `users` row is read for enrollment or promoted.** Historical customer
  accounts are customers.
- **An organization that already has an active owner is skipped**, so a re-run
  cannot put a live tenant's ownership back up for grabs.

Bootstrap invitations carry no token and no expiry, confined to that case by
`ck_organization_invitations_bootstrap`. A migration can neither send mail nor
know when someone will read it, so a seeded invitation with the ordinary
seven-day deadline would be dead before anyone saw it — and an expiring
bootstrap offer would lock every un-migrated organization out of its own
account.

### Calling expansion

`VOICE-EXPANSION.md`'s chunks 06–07 row: *"Browser calling cannot require
organization membership. Revoke call grants/credentials appropriately; V02
implements calling-specific controls."*

- **Nothing in this chunk touches the voice routes**, and personal service is
  never reachable through an organization. `ownership.py` refuses an
  organization any access at all to an order whose payer is a person: an
  employer must not be able to take over a line their employee bought.
- Membership is keyed on `users.id` with no phone, eSIM or device dependency,
  and invitations bind to verified **email** identifiers, so an internet-only
  account is a first-class member.
- Revocation gained an explicit seam: `MembershipService.RevocationListener`,
  invoked inside the revoking transaction. Chunk 07 owns the **moment**; V02
  registers what to withdraw. It is a listener rather than a direct call into
  calling code for a reason that matters — a listener is handed an organization
  and a person, so "revoked membership blocks new work calls **without
  affecting personal service**" is a property of the interface rather than of
  each implementation remembering to check. A listener that raises aborts the
  revocation, rather than leaving a membership removed and its grants live.
- **No call-grant schema is implemented here.** That is V02's, and inventing it
  would put unreviewed tables in the model.

### For Codex specifically

- The permission matrix is one file and is meant to be read as a whole. If
  administrator-holds-`BILLING_MANAGE` is wrong for this product, it is a
  one-line change in `permissions.py` and nothing else moves.
- `may_manage` gives owners an exemption from the rank rule so an owner can
  manage another owner, with the last-owner rule as the only brake. An
  administrator cannot manage a peer administrator, which is the conservative
  direction — it also means only an owner can remove a rogue administrator.
  Worth a second opinion.
- `_acting_membership` re-reads the actor's row inside the handler's own
  session, after the dependency already resolved it. That is two reads per
  privileged request. It is deliberate — the service's row locks must operate on
  live objects — but it is the obvious thing to question.
