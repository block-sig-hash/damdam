### Now

A customer can browse what is on sale, see everything about a plan before
paying, get a server-priced immutable quote, buy it, and — this is the part the
chunk is really about — find their way back to that purchase after any of the
seven ways the journey gets interrupted.

**API (new `app/checkout` package):**

- `GET /v1/catalog/markets`, `GET /v1/catalog/products` — unauthenticated
  browsing. A plan this phone cannot take is **listed** with its price and an
  `unavailable_reason`, not hidden.
- `POST /v1/quotes`, `GET /v1/quotes/{id}` — server pricing from published
  versions only, with an expiry. The read deliberately does **not** re-run
  redemption's checks, so an expired quote reads back `200` with its status
  instead of failing blank.
- `GET /v1/checkout/methods` — what may be paid with, and a reason per refusal.
- `POST /v1/checkout` — **201** for a new order, **200** for one that already
  existed.
- `GET /v1/me/orders`, `GET /v1/me/orders/{id}` — the recovery destination.

**The idempotency decision, stated plainly:** the quote *is* the key. Not a
client `Idempotency-Key` header. A quote is issued once, server-priced, expiring
and redeemable exactly once by a conditional `UPDATE`, so "has this basket
already been bought" is a question PostgreSQL answers without trusting anything
the caller sends. A header would have been a second, weaker key layered over a
strong one, and the two would disagree the first time a client generated a fresh
key for a retry. `CheckoutService.place` looks for an existing intent *before*
touching the quote, routing, or the processor — so a retry is cheap and never
depends on the processor being reachable — and the loser of two simultaneous
checkouts falls back to that same lookup rather than raising at the customer.

**Mobile (`src/screens/Purchase`, `src/api/checkoutClient.ts`,
`src/services/pendingOrder.ts`):** three screens and a flow that owns every
decision that can cost money. Recovery runs *before* browsing: on mount the flow
reads the persisted order first and opens it if there is one, because the surest
way to sell somebody the same eSIM twice is to greet them with a plan list.

**Deliberate choices a reviewer should look at:**

1. **Amounts are strings end to end.** `format_money` is the only place that
   decides how one looks, and the app never does arithmetic on one. A price
   crossing JSON as a float can come back a hundredth different from the one
   that was quoted.
2. **Device facts are tri-state.** `null` (not checked) is not `false` (checked
   and incapable). No platform reports a carrier lock, so `is_unlocked` is
   permanently `null` and only an explicit `false` refuses.
3. **The customer can overrule the eSIM check.** The iOS check is a conservative
   model-generation heuristic; as a verdict it would lock a capable phone out of
   every plan. A negative result is shown with the two checks a person can
   actually perform (an EID in settings, or `*#06#`), and confirming sets the
   fact to `true` with `source: 'customer'`. The app never asserts a capability
   it observed nothing about.
4. **`paymentStarted` is local knowledge, and it changes what the app may say.**
   An `unpaid` order the customer never tried to pay is "you haven't paid yet";
   an `unpaid` order they were sent to the processor for is "we're confirming
   your payment". The server cannot tell these apart — both are an unpaid order
   with an open attempt — and getting it wrong either nags somebody who has paid
   or reassures somebody who has not.
5. **The redirect URL is never persisted.** It is a payment capability, commonly
   with a session token in the query string, and AsyncStorage is unencrypted.
   The order id is enough to recover.

**Deliberately deferred:** no real processor adapter is registered
(`api.state.payment_processor_adapter = None`) — D4 is open, and a default
naming a candidate would be a selection sitting in code where it reads like one
that was made. No basket: one plan per quote from the app, though the API
accepts up to 50 lines and a line for three becomes three independently
recoverable order items.

**Deviation from the assignment:** the assignment's "likely starting points"
named `RetailPurchaseFlow`. That screen is the retired Hajj-era tier purchase
and is left untouched; the reset journey is a new `src/screens/Purchase`. The
assignment itself says paths refer to the inspected baseline and must be
verified against the current checkout.

## Known gaps and handoff

1. **D4 (payment processor) is open, so no payment can actually complete.**
   `payment_processor_adapter` is `None`, every checkout returns
   `awaiting_processor`, and the order is placed, unpaid and resumable. The
   journey is complete up to the point where somebody has to choose a processor.
   *Missing input: the processor selection. Owner: the founder.*
2. **D3 (selling entity) is open, so `collection_enabled` is false everywhere**
   and `tax_configuration_reference` is `null`. The review screen says both in
   words. *Missing input: the selling legal entity and its tax treatment. Owner:
   the founder.*
3. **D2: no market is published**, so a real deployment's catalog is empty. The
   tests seed one. Nothing here publishes a market.
4. **Screenshots are flows, not images.** Chunk 27 is the release gate that
   enforces the matrix; `reset-matrix.json` now claims these eight screens as
   implemented, and `reset-matrix.test.ts` fails if a flow stops capturing one.
5. **`plan-detail` was removed from the pending screenshot matrix**, not left
   owed. The reset has no separate detail screen: price, contents, number policy
   and priced call destinations are all on the plan card, so the customer sees
   them before choosing rather than after a tap. If a reviewer wants a detail
   screen, that is a scope addition, not a missing deliverable.
6. **One plan per quote from the app.** The API takes up to 50 lines and splits
   a quantity into independently recoverable items; the app has no basket, which
   the consumer journey does not need and chunk 23 (bulk provisioning) will.
7. **For Codex:** the two places worth the most scrutiny are
   `CheckoutService.place`'s ordering — existing-intent lookup, then conditional
   redeem, then order/intent/attempt, then the processor last — and
   `PurchaseFlow`'s `paying` ref, which is the only synchronous guard against a
   double tap reaching the network twice. The server makes that second one
   merely cosmetic, which is the intent; it is worth confirming that is still
   true if the quote-as-key decision is ever revisited.
8. **No merge, deployment, store submission, vendor message, live purchase or
   production data deletion was performed.**
